## B. 팀 공유 (계약·형식)
- `BacktestResult.test_period`는 None일 수 있다 (짧은 데이터라 최종 테스트가 없을 때).
- `BacktestResult.calibration` 추가 (선택 필드, 범위 보정 채택 여부와 이동량).
- `ForecastRow`에 `date`, `menu`가 있다 (PROJECT_CONTEXT를 보고 복원한 것이라 원본과 다를 수 있음).
- `signals_used`·`decisions[].signals`에 파생 신호 이름(`temp_diff`, `vacation_diff` 등)이 들어간다. 근거(`reasons`)에는 `*_diff`가 따로 나오지 않는다 (`temp_diff`만 예외: 원재료 `temp_mean`이 모델 변수가 아니므로).
- `chosen_model`은 이름 규칙(M1·M2·M3)을 따른다. 실제로 쓴 신호는 `decisions`와 `signals_used`에 있다.
- 예시 파일: `contracts/examples/` (데모 결과를 복사한 것. 형식이 바뀌면 `run.py --demo` 후 다시 복사).

  - `SignalRow`에 메뉴 칸이 없으므로, 메뉴별 유행 신호를 어떻게 줄지 정해야 한다.

## D. 알려진 한계 (발표·문서에 정직하게)
- **성수 매장의 학습 기간 날씨는 실제 예보가 아니라 관측값(ASOS 서울)이다** (단기예보 API가 최근 3일만 줌, 11/16). 관측값이 예보보다 정확하므로 날씨 신호의 검증 성능은 실제보다 조금 좋게 나온다. 내일 예측에 쓰는 날씨는 실제 예보다.
- 가상 매장에서 선택 모델(M3)이 M0보다 검증 오차가 35.5% 적다 (95% 구간 −43.0%~−29.0%, 블록 부트스트랩). 최종 테스트: M3 WAPE 0.191 vs M0 0.297, 80% 범위 적중 0.76.
- 프랑스 베이커리(실데이터, 신호 없음): 검증 M1 0.299 vs M0 0.408 (−26.6%, 95% 구간 −33.0~−20.1%). 최종 테스트 M1 0.300 vs M0 0.412 (−27%), bias +1%.
  - 단, 이 테스트 구간은 앞에서 한 번 본 것이다(그때 M1이 졌고, 원인 분석에서 이번 수정이 나왔다). 그래서 완전히 독립된 확인은 아니다. 결정 자체는 검증 구간 + 35일 구간 21개로만 했다.
  - 지나온 값: 11/14 −7.1% [−20.3, +9.0] → 11/15 첫날 행 수정 −18.0% → 11/15 `*_diff` 추가 −35.0%. 최종 테스트는 결정에 쓰지 않았다 (모두 검증 구간으로 결정, 테스트는 마지막에 한 번).
  - 가상 데이터는 우리가 만든 효과 그대로라 실제 매장보다 쉽다. 실데이터에서 이 정도를 기대하면 안 된다.
- 신메뉴는 판매 다음 날부터 예측되지만, 처음 며칠은 '최근 평균'이 하루이틀치라 불안정하다 (실험: 1일치 22개 예측 / 실제 수준 31~37개).
- 근거 문장은 모델이 배운 효과이지 인과가 아니다. 11/1 예측(비 9.7mm, 기온이 최근 평균보다 12도 낮음)을 가상 데이터 정답과 비교하면 (11/15 최종 설정):

  | 근거 | 정답 | 모델 | 11/15 아침 |
  |---|---|---|---|
  | 비 | −14% | −16~24% | −20~27% |
  | 아이스 음료, 추운 날 | −38% | −24~31% | −13~18% |
  | 따뜻한 음료, 추운 날 | +52% | +6% | −4% 또는 없음 (방향 틀림) |
  | 빵·디저트, 추운 날 | 0% | 0~−11% (소금빵 −11%) | −4~8% |

  - 방향은 모두 맞게 됐지만 크기는 아직 다르다. 비는 크게, 기온은 작게 잡는다. 12도 차이는 학습 데이터에 드문 극단값이라 나무 모델이 끝까지 따라가지 못한다(나무는 본 범위 밖으로 늘리지 못함).
  - 발표에서 근거 % 숫자를 강조하지 않는다. '방향과 순서'만 믿을 만하다.
- 범위 보정은 이 가상 매장에서 검증을 통과하지 못해 쓰지 않는다 (시기마다 예측이 높게·낮게 번갈아 빗나감).

## F. 코드 지도 (공부 순서대로)

읽는 순서: `contracts/schemas.py`(주고받는 형식) → `run.py`(전체 흐름) → `ml/`(아래 표 순서) → `agent/collect.py`(주변 정보) → `backend/app/main.py` → `frontend/src/`

| 파일 | 한 줄 요약 | 알아야 할 것 |
|---|---|---|
| `contracts/schemas.py` | 팀 공통 데이터 형식 (파일 하나 = 클래스 하나) | pydantic `BaseModel`, `Field(ge=0)`, `Literal`, `model_validator`. `StoreConfig` = store.json |
| `ml/paths.py` | 폴더 위치 | `ROOT`·`SAMPLE`·`RAW`·`ARTIFACTS` |
| `ml/sample_data.py` | 효과를 심어 둔 가상 매장 1년치 | 난수 시드, 감마-포아송 잡음 |
| `ml/ingest.py` | POS 파일 → 판매 기록 | 머리글 자동 찾기, 0개 판매 채우기, 품절 '쌓임' 판정, `difflib`, 자모 분해(NFD) |
| `ml/features.py` | 모델 입력 표 | **시점 규칙(issue_time)**, `shift(1)` 후 `rolling`, 신호의 '가장 늦은 발표본', 파생 신호(`DERIVED_SIGNALS`: 목표가 '최근 평균 대비'라 신호도 '최근 평균 대비') |
| `ml/models.py` | M0 + CatBoost 다중 분위 | 비율 목표(qty/평소 수준), MultiQuantile, 원-핫 vs target statistics, 시드 평균(분산 줄이기) |
| `ml/metrics.py` | 지표 | WAPE·pinball·coverage, 품절 행 제외(`scored`), 블록 부트스트랩 |
| `ml/calibration.py` | 예측 범위 보정 | conformal(평소 수준 대비 이동량)과 그 채택 검사 |
| `ml/evaluate.py` | 검증 → backtest.json | 시간순 교차검증(`plan_folds`·`cross_val_predict`), 신호 조합 선택(`choose_signals`·`pick_combo`·`beats`), 최종 테스트 한 번 |
| `ml/predict.py` | 내일 예측 → forecast.json | 반사실 근거(`explain`: 신호를 평소 값으로 바꿔 다시 예측), 준비량(p40/p50/p80 올림) |
| `ml/alerts.py` | AI 주의 안내 (LLM 특수 상황 경고) | 시점 규칙으로 원문 거르기, 인용 검증, 영향 메뉴 정리 |
| `ml/llm.py` | `.env` 설정 읽기 + Claude 호출 | structured outputs(`messages.parse`), 입력 해시 캐시, 제공자 사전(`PROVIDERS`) |
| `run.py` | 한 매장 전체 실행 | `argparse`, `--from-step`, 단계 함수(`step_ingest`·`step_evaluate`·`step_predict`) |
| `agent/collect.py` | 주변 정보 수집의 입구 | 정보원 하나 = 함수 하나(`SOURCES`), 모두 (신호, 원문, 메모)를 돌려줌 |
| `agent/collectors_bridge.py` | 공공 데이터 수집기 실행 + 결과 → 신호·원문 | `subprocess`, 공개 시각 붙이는 규칙(관측값은 '전날 17:10 예보'처럼), 행사 수가 등록될 때마다 늘어나는 줄 |
| `agent/report.py` | 수집 결과 요약 → sources_report.json | 화면 '주변 정보'의 재료. 계산 없이 파일 요약만 |
| `agent/events.py` | 뉴스·블로그·공지 글 → 행사 신호 | LLM은 날짜·장소만, 근거 문장 대조, 거리(haversine), 취소는 value 0 |
| `agent/naver.py` | 네이버 검색, 메뉴 유행 신호 | 게시 시각을 읽은 시각 이하로, `trend_level`(최근 7일 ÷ 그 전 28일, D−2일까지만) |
| `agent/geocode.py` | 주소·장소 → 좌표 | 카카오 → OpenStreetMap, 결과 저장(못 찾은 것도) |
| `backend/collectors/` | 공공 데이터 수집기 (새얼) | 실행 순서(`run_all.py`), 정보원 선택 에이전트(`agent.py`)의 검증 규칙 |
| `backend/app/main.py` | 웹 API | `run.py`를 별도 프로세스로, 작업 상태 폴링, 시연 모드(보기 전용) |
| `backend/app/auth.py` | 구글·카카오 로그인, 매장 접근 권한, 내 매장 등록 | ID 토큰 검증(구글), 인가 코드 방식(카카오), 세션 쿠키(HttpOnly), SQLite, 주인·관리자 규칙 |

**직접 검증 (파일마다 손으로 하나씩)**
먼저 `run.py --store sinchon-a --demo`를 실행해 `data/artifacts/sinchon-a/`에 결과를 만든 뒤 아래를 확인한다.
1. `schemas.py`: `contracts/examples/forecast.json`의 칸 하나하나가 어느 클래스·필드인지 짝짓는다.
2. `ingest.py`: `data/artifacts/fr-bakery/ingest_log.json`을 열고, 원본 CSV에서 하루·메뉴 하나(예: 2021-01-02 BAGUETTE)의 수량을 직접 더해 `sales_clean.csv`의 값과 같은지 본다.
3. `features.py`: `build_frame`으로 표를 만들고, 한 행(메뉴·날짜)의 `lag_7`·`mean_28`·`r_mean_7`·`store_7_28`을 `sales_clean.csv`에서 계산기로 다시 구한다. D일 행에 D일 판매가 섞이지 않았는지가 핵심이다.
4. `models.py`: 그 행의 p50 = (모델이 낸 비율) × base_level인지 확인한다. `y = qty / base`가 왜 필요한지 설명해 본다.
