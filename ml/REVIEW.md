## B. 팀 공유 (계약·형식)
- `BacktestResult.test_period`는 None일 수 있다 (짧은 데이터라 최종 테스트가 없을 때).
- `BacktestResult.calibration` 추가 (선택 필드, 범위 보정 채택 여부와 이동량).
- `ForecastRow`에 `date`, `menu`가 있다 (PROJECT_CONTEXT를 보고 복원한 것이라 원본과 다를 수 있음).
- `signals_used`·`decisions[].signals`에 파생 신호 이름(`temp_diff`, `vacation_diff` 등)이 들어간다. 근거(`reasons`)에는 `*_diff`가 따로 나오지 않는다 (`temp_diff`만 예외: 원재료 `temp_mean`이 모델 변수가 아니므로).
- `chosen_model`은 이름 규칙(M1·M2·M3)을 따른다. 실제로 쓴 신호는 `decisions`와 `signals_used`에 있다.
- 예시 파일: `contracts/examples/` (데모 결과를 복사한 것. 형식이 바뀌면 `run.py --demo` 후 다시 복사).
- 새얼:
  - `published_at`이 한국 시간(KST)인지 확인한다.
  - `SignalRow`에 메뉴 칸이 없으므로, 메뉴별 유행 신호를 어떻게 줄지 정해야 한다.
  - **기념일 신호 요청:** `signal="special_day"`, `kind="calendar"`, `value=1`. 발렌타인·화이트데이·빼빼로데이·크리스마스(이브) 등 해당하는 날만 행을 넣는다 (없는 날은 0으로 처리됨).
  - **`collection.json` 형식을 확정해야 한다.** 지금은 `[{"date", "title", "text", "source_url"}]`로 가정했다. `data/artifacts/{store}/collection.json`에 두면 경고가 만들어진다.
- 실행 명령: `python run.py --store {id} --demo` 또는 `--pos {파일} --signals {파일}`

## D. 알려진 한계 (발표·문서에 정직하게)
- 가상 매장에서 선택 모델(M3)이 M0보다 검증 오차가 35.5% 적다 (95% 구간 −43.0%~−29.0%, 블록 부트스트랩). 최종 테스트: M3 WAPE 0.191 vs M0 0.297, 80% 범위 적중 0.76.
- 프랑스 베이커리(실데이터, 신호 없음): 검증 M1 0.299 vs M0 0.408 (−26.6%, 95% 구간 −33.0~−20.1%). 최종 테스트 M1 0.300 vs M0 0.412 (−27%), bias +1%.
  - 단, 이 테스트 구간은 앞에서 한 번 본 것이다(그때 M1이 졌고, 원인 분석에서 이번 수정이 나왔다). 그래서 완전히 독립된 확인은 아니다. 결정 자체는 검증 구간 + 35일 구간 21개로만 했다.
  - 지나온 값: 11/14 −7.1% [−20.3, +9.0] → 11/15 첫날 행 수정 −18.0% → 11/15 `*_diff` 추가 −35.0%. 최종 테스트는 결정에 쓰지 않았다 (모두 검증 구간으로 결정, 테스트는 마지막에 한 번).
  - 가상 데이터는 우리가 만든 효과 그대로라 실제 매장보다 쉽다. 실데이터에서 이 정도를 기대하면 안 된다.
- 신메뉴는 판매 다음 날부터 예측되지만, 처음 며칠은 '최근 평균'이 하루이틀치라 불안정하다 (실험: 1일치 22개 예측 / 실제 수준 31~37개).
- 근거 문장은 모델이 배운 효과이지 인과가 아니다. 11/1 예측(비 9.7mm, 기온이 최근 평균보다 12도 낮음)을 가상 데이터 정답과 비교하면 (11/15 최종 설정):

  | 근거 | 정답 | 모델 | 11/15 아침 |
  |---|---|---|---|
  | 비 | −14% | −16~24% | −20~27% |
  | 아이스 음료, 추운 날 | −38% | −24~31% | −13~18% |
  | 따뜻한 음료, 추운 날 | +52% | +6% | −4% 또는 없음 (방향 틀림) |
  | 빵·디저트, 추운 날 | 0% | 0~−11% (소금빵 −11%) | −4~8% |

  - 방향은 모두 맞게 됐지만 크기는 아직 다르다. 비는 크게, 기온은 작게 잡는다. 12도 차이는 학습 데이터에 드문 극단값이라 나무 모델이 끝까지 따라가지 못한다(나무는 본 범위 밖으로 늘리지 못함).
  - 발표에서 근거 % 숫자를 강조하지 않는다. '방향과 순서'만 믿을 만하다.
- 범위 보정은 이 가상 매장에서 검증을 통과하지 못해 쓰지 않는다 (시기마다 예측이 높게·낮게 번갈아 빗나감).

- 11/15 **근거 문장 다시 재기 → 세 가지 수정.** (모두 검증 구간으로만 판단)
  1. **`menu_temp` 변수** (`features.py`, 'ICE'/'HOT'/'-', `ingest.temp_tag`): 메뉴마다가 아니라 '따뜻한 음료끼리' 기온 효과를 함께 배우게 한다. 정확도는 그대로(시드 차이 안), 따뜻한 음료 근거 방향이 맞게 됨.
  2. **시드 3개 평균** (`models.CatBoostQuantile`, `n_seeds=3`): 시드 하나만 바꿔도 검증 WAPE가 0.275~0.285로 흔들리고 학사일정 채택이 뒤집혔다. 3개 평균이면 시작 시드 4가지에서 채택이 모두 같고, 최종 테스트도 0.204~0.209로 좁아졌다(1개일 때 0.202~0.236). 시간 약 2.5배.
  3. **학사일정 `*_diff` 파생 신호** (`exam_period_diff`·`vacation_diff`·`festival_diff` = 오늘 값 − 최근 28일 평균, `temp_diff`와 같은 방식): 방학이 시작되면 '최근 평균'(목표의 기준)이 한동안 학기 수준이라 모델이 과대 예측하고, 그 오차를 '추워졌다'가 대신 떠안아 빵 근거가 틀렸다. 검증 WAPE M3 0.279 → 0.219, bias +5% → +1%.
     - 근거 계산(`predict.py`)은 원재료와 파생을 함께 바꾼다 (`vacation`을 평소 값으로 → `vacation_diff`도 그만큼). 그래서 근거는 "방학 기간이라 …" 한 줄로 나온다.
     - '원재료만'과 '파생만'도 시험: 파생만 쓰면 WAPE는 비슷(0.215~0.218)하지만 근거 문장이 어색해져 둘 다 넣었다.

- 11/15 **프랑스 베이커리 실데이터로 검증** (Kaggle, `data/Bakery sales.csv`, 영수증 단위 23만 행, 2021-01~2022-09, 600일·메뉴 149개).
  - 방법: 열 이름만 한국 POS 머리글로 바꾼 사본을 `run.py --pos`로 실행 (11/18과 같은 경로). 결과: `data/artifacts/fr-bakery/`. 코드 수정 없이 끝까지 돌았다 (38초).
  - ingest: 수요일 휴무 37일을 휴무로 찾음, 품절 추정 0건, 단종 75개(계절 메뉴), 취소 1,295행 제외.
  - **공식 결과 (신호 없음, 미리 정한 규칙 그대로):** 검증 WAPE M1 0.367 vs M0 0.408 (−10.0%, 95% 구간 −21.9~−2.5%). **그러나 최종 테스트(2022-09)는 M1 0.514 vs M0 0.412로 M0보다 나빴다** (과대 예측 +27%).
  - 원인: 관광지 매장이라 7~8월 하루 약 1,000개 → 9월 약 480개로 반 넘게 준다. 9월 첫 2주는 '최근 28일 평균'이 아직 8월 수준이라 M1이 40~50% 과대 예측. 3주째부터는 M0와 같거나 낫다. 가상 데이터에서 `vacation_diff`로 고친 것과 같은 문제다.
  - **사후 실험 (테스트를 본 뒤라 공식 결과가 아님):** 프랑스 학교 방학(전국 공통 기간: 여름·만성절·성탄)을 `vacation` 신호로 넣으면, 검증 규칙이 스스로 채택(4개 구간 중 3개 개선, −6.9%) → 최종 테스트 0.355 vs M0 0.412 (−14%). 대신 과소 예측 −16%로 방향이 뒤집혔다.
  - 발표에서 쓸 수 있는 말: "실제 매장 데이터에서도 검증 기간에는 기준선보다 10% 나았지만, 성수기가 끝나는 달에는 졌다. 원인은 시기 정보가 없었던 것이고, 학교 방학 달력을 넣으면 14% 나아졌다(사후 실험)."
  - 메뉴명 통일 후보 51쌍 중 27쌍이 'TARTE 4P'↔'6P' 같은 크기 차이 → **이름 속 숫자가 다르면 후보에서 뺀다** (`suggest_menu_merges`). 남은 24쌍도 대부분 다른 메뉴(GD/PT = 큰/작은)라 승인할 때 주의.

- 11/15 **'성능이 안 나온다' → 오차 분해 후 이력 변수를 비율로 + 매장 전체 흐름 추가** (`features.HISTORY_FEATURES`).

  - 검증 WAPE: 베이커리 M1 0.367→0.299, 가상 M1 0.327→0.291, 가상 M3 0.219→0.218(신호가 이미 잡던 것이라 그대로).

| 파일 | 한 줄 요약 | 알아야 할 것 |
|---|---|---|
| `contracts/schemas.py` | 팀 공통 데이터 형식 | pydantic `BaseModel`, `Field(ge=0)`, `Literal`, `model_validator` |

| `ml/ingest.py` | POS 파일 → 판매 기록 | 머리글 자동 찾기, 0개 판매 채우기, 품절 '쌓임' 판정, `difflib`, 자모 분해(NFD) |
| `ml/features.py` | 모델 입력 표 | **시점 규칙(issue_time)**, `shift(1)` 후 `rolling`, 신호의 '가장 늦은 발표본', 파생 신호(`DERIVED_SIGNALS`: 목표가 '최근 평균 대비'라 신호도 '최근 평균 대비') |

| `ml/evaluate.py` | 검증 → backtest.json | WAPE·pinball, 시간순 교차검증, 신호 조합 선택(`pick_combo`·`beats`), 범위 보정(conformal)과 그 채택 검사, 블록 부트스트랩 |
| `ml/predict.py` | 내일 예측 → forecast.json | 반사실 근거(신호를 평소 값으로 바꿔 다시 예측), 준비량(p50/p60/p80 올림) |
| `ml/alerts.py` | LLM 특수 상황 경고 | structured outputs(`messages.parse`), 입력 해시 캐시, 인용 검증 |
| `run.py` | 한 매장 전체 실행 | `argparse`, `--from-step`, 함수 사전 |

**직접 검증 (파일마다 손으로 하나씩)**
먼저 `run.py --store sinchon-a --demo`를 실행해 `data/artifacts/sinchon-a/`에 결과를 만든 뒤 아래를 확인한다.
1. `schemas.py`: `contracts/examples/forecast.json`의 칸 하나하나가 어느 클래스·필드인지 짝짓는다.
2. `ingest.py`: `data/artifacts/fr-bakery/ingest_log.json`을 열고, 원본 CSV에서 하루·메뉴 하나(예: 2021-01-02 BAGUETTE)의 수량을 직접 더해 `sales_clean.csv`의 값과 같은지 본다.
3. `features.py`: `build_frame`으로 표를 만들고, 한 행(메뉴·날짜)의 `lag_7`·`mean_28`·`r_mean_7`·`store_7_28`을 `sales_clean.csv`에서 계산기로 다시 구한다. D일 행에 D일 판매가 섞이지 않았는지가 핵심이다.
4. `models.py`: 그 행의 p50 = (모델이 낸 비율) × base_level인지 확인한다. `y = qty / base`가 왜 필요한지 설명해 본다.
5. `evaluate.py`: `backtest.json`의 `folds`·`test_period` 날짜가 서로 겹치지 않는지, WAPE를 예측표에서 직접 다시 계산해 같은지 본다. 신호 채택 문장(`decisions.reason`)이 규칙과 맞는지 본다.
6. `predict.py`: 11/1 예측에서 `rain_mm`을 0으로 바꿔 다시 예측하면, 근거 문장의 %가 나오는지 본다.
7. `alerts.py`: 가짜 `collection.json`(인용이 원문에 없는 경고 포함)으로 `tests/test_alerts.py`를 읽고, 지어낸 인용이 왜 걸러지는지 따라간다.
8. 일부러 고장 내기: `features.py`의 `past = qty.shift(1)`을 `qty`로 바꾸고 `pytest`를 돌려 누수 테스트가 실패하는지 본다 (확인 후 되돌리기).
